# Ad Click Aggregator

## Scope and assumptions

Design ingestion and aggregation for click events generated by ad impressions. Advertisers and internal dashboards query counts by dimensions such as campaign, creative, placement, and time window. The system must handle retries, bursts, delayed events, and invalid traffic. It does not choose which ad to show, calculate a full invoice, or determine fraud with perfect accuracy; those systems consume validated events and reconciled aggregates.

## Requirements and exclusions

**Required:** accept high-volume click events; validate identifiers and signatures; deduplicate retries; aggregate by useful dimensions and time; provide fresh queries; retain raw evidence for audit and correction.

**Quality:** tolerate ingestion spikes and consumer failures, communicate freshness, and make financial-grade consumers distinguish preliminary from reconciled totals. Online dashboard results may be approximate or provisional.

## Data model and API

`ClickEvent(event_id, impression_id, campaign_id, creative_id, placement_id, event_time, received_at, user_or_device_token, signature, schema_version)` is the normalized event. Avoid storing unnecessary direct personal data. A deduplication key can be `event_id`, or `(impression_id, click_sequence)` when producers guarantee uniqueness. Aggregate keys are `(campaign_id, dimension_set, window_start)` with count and optional quality status. Keep raw immutable events or compacted references under a retention policy.

API: `POST /clicks` or a batched ingestion endpoint returns accepted/rejected counts and a request ID. Query API: `GET /reports/clicks?campaign=...&from=...&to=...&group_by=...` returns aggregates, `as_of`, and `provisional` status. Enforce allowed dimensions and bounded time ranges.

## Architecture

Edge ingestion validates authentication, schema, timestamp bounds, and basic abuse controls, then writes to a replicated durable event log. A stream processor performs idempotent deduplication, enriches events with campaign metadata, filters obvious invalid traffic, and aggregates into short time buckets. Raw event storage supports replay and audit. A serving store optimized for grouped range queries exposes dashboard results. A batch reconciliation pipeline recomputes finalized windows from raw data, applying stronger fraud rules and late-arrival corrections. A catalog/cache supplies versioned campaign metadata.

## End-to-end flow

1. Ad client or trusted server submits an event with stable IDs and an integrity token. Gateway authenticates, applies schema and rate checks, and assigns `received_at`.
2. Accepted records are appended to a partitioned log before success is returned, preventing an acknowledged click from existing only in process memory.
3. Stream workers deduplicate by event key within a defined retention window and check basic eligibility, such as a valid impression and plausible time relationship.
4. Valid events are enriched using versioned campaign data and counted in event-time buckets. Invalid or suspicious events are retained with reason codes when policy permits.
5. Aggregates are written idempotently or via checkpointed transactions; API reads recent buckets and returns freshness/provisional flags.
6. Batch jobs replay retained raw data after late events or improved fraud classification, then publish corrected finalized aggregates with a new version.
7. Downstream billing consumes only the agreed finalized dataset and reconciliation watermark, not an unqualified dashboard count.

## Scaling, consistency, and reliability

Partition the log by a hash of impression or event ID for even ingestion, then repartition by campaign for aggregation. Popular campaigns can become hot keys; shard partial counters and merge them at query or compaction time. Batch updates to the serving store to reduce write amplification. Use event time for reporting, but cap how far back events can claim to have occurred. Watermarks close a window after an allowed lateness period; late arrivals can revise it until a finalization policy says otherwise.

Exactly-once processing is usually an end-to-end illusion built from at-least-once delivery plus durable deduplication and idempotent writes. Keep dedup state at least as long as producer retry horizons, and define behavior after expiry. Store raw events separately from aggregates so a bug can be corrected by replay. For consistency, dashboard data may be eventually updated; finalized reports must identify data version, completeness, and correction history. Never expose a bare number without its interval and freshness.

Privacy matters: pseudonymous identifiers should be purpose-limited, access-controlled, and retained only as long as needed for deduplication or fraud policy. Aggregates should suppress small groups if they could expose individuals.

## Deep dives and failure cases

**Duplicate and fabricated events:** A client can retry after a timeout or replay a valid payload. Stable event IDs make retries idempotent; signatures, impression linkage, velocity rules, and downstream fraud classifiers reduce abuse. Deduplication is not fraud detection: a unique event may still be invalid. Keep a reasoned audit trail and allow retroactive adjustment.

**Processor outage:** The durable log buffers events while consumers recover. Monitor partition lag and oldest unprocessed event. If retention is at risk, apply backpressure or reject with retry guidance rather than acknowledge and silently drop. On replay, checkpoint boundaries and idempotent aggregate versions prevent duplicated counts.

## Quick recall

Durable ingest first, deduplicate and validate in a stream, aggregate by event-time windows, and preserve raw events for replay. Separate provisional dashboards from finalized billing, expose freshness/version, and treat dedupe and fraud as distinct problems.
